# CLAUDE.md — sunset-mobile

Two native apps (staff, guest) for the `sunset` backend. Read `sunset`'s CLAUDE.md and
`openapi.yaml`, and `sunset-beach`'s CLAUDE.md, before changing behaviour: this repo follows the
same server-is-truth rules. Rules below are this repo's own additions.

## Two audiences, never mixed

- `apps/staff` imports only `@sunset/api-client/staff`; `apps/guest` only `@sunset/api-client/guest`.
  Never import both into one app - `npm run verify` greps each bundle for the other audience's
  client and token key and fails if it finds them.
- The guest client's *type* has no staff paths, and its runtime scope throws `ScopeViolation`
  before any request leaves the device. Don't "fix" a ScopeViolation by widening the scope: the
  backend currently lets a guest token through some staff `authenticated()` routes (audit finding
  H1, a backend bug) - the guest app must never rely on that.
- Each app keeps exactly one token, in `expo-secure-store` (Keychain/Keystore), never AsyncStorage.
  The guest token is sent only to `/guest/**`.
- Token revocation (`tokenVersion`) needs nothing client-side: a 401 on a token-bearing call means
  "sign in again" (`onUnauthorized`). Don't build local revocation logic.

## API types are generated, never written

`packages/api-client/src/schema.ts` comes from `openapi-typescript` over the vendored
`openapi.yaml`. Never hand-write or hand-edit an API type - the web client's hand-mirrored types
drifted from the spec on nullability (audit finding M7). If the spec is wrong, fix it in `sunset`
first, re-sync, regenerate.

## Money

Display only the server's decimal strings (`formatBaht`). No totals, sums or per-night maths on the
device: the guest booking price comes from `GET /public/rooms/{id}/quote`, an order's total from
`Order.total`/`GuestOrderView.total`, a cart has no total at all. The one exception, as on the web,
is cash change (`cashChange`): notes in hand minus the server's total, in integer satang.

Shift close shows the server's totals and the counted figure only - there's no server field for
"expected cash" yet, so the app doesn't compute one (see "Known gaps").

## Dates

"Today" is the hotel's day (`hotelDateKey`, Asia/Bangkok), never the phone's zone. Stay dates are
keys stepped with `addDays` (UTC arithmetic); no date library.

## UI rules carried over from the web

- Hide what a role can't do (`lib/access.ts`, mirrors `SecurityConfig`) *and* guard the screen
  (`RequireCapability`). Job functions are their own axis (`ENGINEER` closes maintenance tasks).
- A failure shows next to the control that caused it; a failed reload keeps the last data.
- Polls never overwrite newer state (`useLoad` + `createLatestGuard`).
- "Not printed" = FAILED + PENDING, one rule for every counter.
- Money actions on the shared floor phone name who they'll be recorded as (`confirmAsActor`);
  30 minutes untouched signs the staff app out.

## Expo

Expo SDK 57. Expo's APIs change every SDK - check the installed package's `.d.ts` (or the
versioned docs) instead of memory. Add native packages with `npx expo install` (in this sandbox:
`EXPO_OFFLINE=1 npx expo install …`). `ios/` and `android/` are generated by prebuild and ignored.

**Web is a preview, never a shipped target.** `npm run staff:web|guest:web` exists so a person (or
a Playwright walk-through) can click through the screens without a phone. Two `.web.ts` files make
that work and must stay the only web-specific code:
- `lib/secureStore.web.ts` keeps tokens in memory. A browser has no secure storage, and
  localStorage would hand the token to any script on the page - don't "fix" the reload sign-out
  by persisting it.
- `lib/ask.web.ts` (staff): react-native-web's `Alert.alert` is a silent no-op, so every
  confirmation goes through `ask()`, never `Alert.alert` directly - otherwise a money action is a
  dead button in the preview.

The backend's CORS allows GET/POST/PATCH/DELETE only (the web admin is same-origin and never needed
more), so a `PUT` - assigning a room - fails in the browser preview with a CORS error and works on a
phone, where there is no CORS. Check a `PUT` against the API directly, not through the preview.

Label inputs and buttons with `aria-label`/`role`, not `accessibilityLabel`/`accessibilityRole`:
RN 0.86 supports both on device, but react-native-web 0.21 only renders the `aria-*` ones, and the
UI kit's `Field` relies on it to tie each input to its label.

`npm run dev:backend` (`tools/dev/backend.ts`) is the only place demo data is defined. Keep it
realistic - a stay is confirmed before check-in, because the POS only charges CONFIRMED/PAID
bookings to a room (same rule as the web POS); an unrealistic seed hides real bugs.

## Staff app releases (Android, self-hosted)

The staff APK and its JavaScript updates are static files on the hotel's VPS, published by
`tools/dev/release.ts` and served by `deploy/nginx-mobile.conf` - not Play Store, not EAS Update
(RELEASING.md). `tools/dev/updateManifest.ts` writes the Expo Updates protocol-1 manifest in the
exact shape expo-updates' Android loader parses (checked against its Kotlin source, since the docs
weren't reachable): every file is named by and checked against its SHA-256, and the nginx `map`
picks the manifest by `Expo-Platform` + `Expo-Runtime-Version` (an `if` in that location would
silently disable `try_files` - that was the first version's bug). `runtimeVersion` is the app
version: bump it (`release -- bump --native`) whenever native code changes, or a phone gets
JavaScript for native modules it doesn't have. A release always uses the production URLs in
`release.ts`, never `apps/*/.env`.

## Known gaps (need a backend change first)

- No "my own attendance punches" endpoint for ordinary staff (`/attendance/**` is MANAGER+), so the
  staff app shows punches only to managers (today's board) and "my schedule" to everyone.
- `ShiftSummary` has no `expectedCash`/`discrepancy`, so the shift screen can't show them without
  computing money on the device.
- No push notifications in v1 (nothing on the backend sends them yet).
